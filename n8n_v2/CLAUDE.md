# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this directory is

This is a self-hosted [n8n](https://n8n.io) deployment directory generated by the `get-n8n.sh` installer from https://get.n8n.io (installer v1.3.0), plus the salon-assistant agent workflow built on top of it. The installer-owned part is exactly three files:

- `compose.yml` — the whole stack definition (6 services). Owned by you; the installer never rewrites it.
- `.env` — generated secrets and version pin, shared by every service via `env_file: .env`. Not in version control (this directory is not a git repo).
- `searxng-settings.yml` — bind-mounted read-only into the SearXNG container.

For the stack itself there is no build, lint, or test step — it is YAML/env editing and Docker Compose. The agent workflow under `salon-assistant/` does have a build and two test suites (see the last section).

`PLAN.md` tracks an in-progress build: a customer-service AI agent for a haircut business (booking, stylist matching, hairstyle/hair-type consultation, haircare promotions), prototyped on n8n Cloud and migrated back to this stack. Read it before touching agent-workflow work — it carries hard constraints (no fabricated prices/promotions, no photo-based hair-type inference, no health advice) that are design requirements, not preferences.

## Commands

```bash
docker compose up -d          # start (or apply changes to) the stack
docker compose ps             # service status
docker compose logs -f n8n    # follow one service; swap in sandbox-api, sandbox-runner-1, runners, searxng
docker compose down           # stop; named volumes survive
docker compose restart n8n    # restart a single service after an .env change
```

n8n UI: http://localhost:5678.

Upgrades go through the installer (`get-n8n.sh --upgrade`), which edits only the `N8N_VERSION` line in `.env` and nothing else. `N8N_VERSION` pins **both** `n8nio/n8n` and `ghcr.io/n8n-io/runners` — those two images must stay on the same tag. Current pin: 2.37.10.

To review upstream changes to the stack definition between installer versions: https://github.com/n8n-io/n8n/commits/master/docker/get-n8n-compose.yml (`compose.yml` carries a `# compose-version:` marker for this).

## Architecture

Six services on the default Compose network, reaching each other by service name. Three concerns are deliberately split out of the n8n container:

**1. Code-node execution → `runners`.** `N8N_RUNNERS_MODE=external` makes n8n run a task broker on port 5679 (bound `0.0.0.0` so the sibling container can reach it, never published). The `runners` container connects to `http://n8n:5679` with `N8N_RUNNERS_AUTH_TOKEN` and executes user JavaScript/Python from Code nodes. Idle runners self-terminate after 15s and are relaunched on demand.

**2. AI-assistant sandboxing → `sandbox-certs` / `sandbox-api` / `sandbox-runner-1`.** A three-stage chain:

- `sandbox-certs` is a one-shot bootstrap (`bootstrap-mtls.sh`) that writes a CA plus per-side cert/key pairs into the `sandbox-tls` volume, then exits. `sandbox-api` waits on `service_completed_successfully`; the runner waits on `sandbox-api` being healthy.
- `sandbox-api` (8080 HTTP, 9090 gRPC) is both a gRPC *server* to runners registering with it and a gRPC *client* to each runner's control plane — hence two cert sets in its environment, with `SANDBOX_API_RUNNER_CONTROL_GRPC_TLS_SERVER_NAME` pinned to `sandbox-runner-1`.
- `sandbox-runner-1` is **privileged Docker-in-Docker**; it launches `n8n-sandbox-service-sandbox` containers for AI-generated code. n8n talks to the sandbox only via `sandbox-api` (`N8N_INSTANCE_AI_SANDBOX_API_URL` / `N8N_SANDBOX_SERVICE_URL`).

Scaling to more runners means adding a `sandbox-runner-N` service **and** raising `NUM_RUNNERS` on `sandbox-certs` (it decides how many `sandbox-runner-*` SANs get issued) — then wiping the `sandbox-tls` volume so certs are reissued.

**3. Web search → `searxng`.** Reached at `http://searxng:8080` via `N8N_INSTANCE_AI_SEARXNG_URL`. Setting `INSTANCE_AI_BRAVE_SEARCH_API_KEY` in `.env` takes priority over SearXNG. `searxng-settings.yml` must keep `json` in `search.formats` — n8n consumes the JSON API, which upstream SearXNG disables by default.

### Port exposure

`5678` (n8n) is the only port that should ever be internet-facing. Do not add `ports:` entries for `sandbox-api` (8080/9090), `sandbox-runner-1` (privileged DinD), `runners`, or `searxng` — the comments in `compose.yml` marking this are load-bearing security constraints, not style notes.

### Volumes

- `n8n-data` → `/home/node/.n8n`: all workflows, credentials, and the SQLite database. Destroying it destroys the install.
- `sandbox-tls`: mTLS material; safe to delete — `sandbox-certs` regenerates it on the next `up`.

## Working with `.env`

Several secrets are **paired** — the API side and the client side must hold the same value, so rotating one means rotating its twin in the same edit:

| API side | Client side |
| --- | --- |
| `SANDBOX_API_KEYS` | `N8N_SANDBOX_SERVICE_API_KEY` |
| `SANDBOX_API_RUNNER_REGISTRATION_TOKEN` | `SANDBOX_RUNNER_REGISTRATION_TOKEN` |
| `SANDBOX_API_RUNNER_API_KEY` | `SANDBOX_RUNNER_API_KEYS` |

Because every service uses `env_file: .env`, an edit there affects the whole stack — `docker compose up -d` to apply. Values in a service's `environment:` block override `.env` for that service.

## Salon assistant workflow (`salon-assistant/`)

`salon-assistant-v2.json` is **generated** — never hand-edit it. Sources: `salon-assistant/code/*.js` (one file per Code node / Code Tool), assembled by `salon-assistant/build.js` (also holds the system prompt, tool schemas, node wiring).

```bash
cd salon-assistant && node build.js && node verify.js && node verify2.js   # rebuild + 88 logic checks
cd salon-assistant && node run_chat.js                                     # 18 live conversations against the local webhook
node salon-assistant/make_tables.js                                        # mockdata.jsonc -> tables.json (Data Table columns/rows)
```

`verify*.js` execute each node's `jsCode` under `new Function` with a stubbed `$()` / `query`, so they prove logic, not n8n integration; `run_chat.js` is the integration check and needs the workflow active on `localhost:5678`. Local table IDs, workflow ID and webhook are recorded in PLAN.md §11. Deploying a rebuilt JSON to the running instance means PATCH + activate via the n8n REST API with a browser session (or re-import in the UI); the CLI `n8n import:workflow` upserts by id but does not re-activate.

Design rules that the tests enforce (see comments in `code/`): tools resolve customer words to IDs themselves; empty results carry a `final_instruction`; the renderer is evidence-first and the model never emits prose; all tool input fields are optional; write tools are stubs gated on explicit confirmation.
